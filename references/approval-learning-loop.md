# Approval learning loop

Use this loop when a person reviews a draft, deck, site, document, or generated design and wants the judgment to improve the next run.

The approved final is the source of truth. A writing or design tool is useful as a second opinion. It is not the author of the voice profile and it is not the memory.

## Compare the three states

Keep these side by side:

1. the original or current approved artifact;
2. the proposed revision;
3. the human-approved final.

Review four layers separately:

- meaning: claims, evidence, caveats, and required steps;
- voice: vocabulary, rhythm, confidence, and point of view;
- hierarchy: what appears first, what is grouped, and what is deferred;
- presentation: typography, spacing, diagrams, imagery, and interaction.

Do not call a change an improvement because it looks more polished. Check whether it made the artifact clearer without changing the claim or hiding an operating detail.

## Record the decision

For each meaningful change, record:

- before;
- proposal;
- approved final;
- verdict: adopt, reject, or contextual;
- why;
- reusable rule;
- protected detail;
- a future test that would catch regression.

Keep the record short. Store the judgment, not private source material. Do not publish customer details, internal screenshots, or confidential examples in a public voice profile.

## Promote carefully

One approval can update the current artifact. Promote the choice to a durable profile rule only when the writer explicitly says it should compound or when more than one approval confirms the same preference.

Use three levels:

- artifact: applies only to the current piece;
- channel: applies to a format such as paid courses, executive updates, or LinkedIn;
- durable voice: applies broadly across the writer's work.

Record rejections as well as adoptions. A rejected pattern prevents the next run from spending time rediscovering the same mistake.

## Decide whether another tool call is worth it

Read the existing profile and approval decisions first. Apply them locally before using another external tool.

Use a new tool pass only when at least one of these is true:

- the person explicitly asks for it;
- there is a named design question the current rules cannot resolve;
- the medium changed enough that the old decision may not transfer;
- a fresh pass can test a meaningful alternative, not merely produce more options.

By default, use one external comparison for a major new surface. Do not regenerate to chase taste. If the approved rules already answer the question, make the change directly and spend the review time on accuracy, usability, and evidence.

## Check the next artifact

Before delivery, ask:

- Did the new draft apply the accepted decision?
- Did it avoid the rejected pattern?
- Did the edit preserve every required claim and operating step?
- Is the rule still useful outside the original example?
- Would removing the rule make the writing more accurate or more recognizable?

If the rule makes later work blander, less accurate, or less recognizably the writer's, demote it to a channel choice or remove it.
